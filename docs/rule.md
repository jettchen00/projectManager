# projectManager的工作守则


## 1. 规则速查表

| 编号  | 规则                                       | 级别 |
|-----|------------------------------------------|------|
| R01 | 每次修改代码后必须保证编译通过(windows机器的话，不要运行编译指令)    | **强制** |
| R02 | 只允许修改 projectManager的工作守则 目录下的文件         | **强制** |
| R03 | AI 工具不得自行提交代码                            | **强制** |
| R04 | 遵循分层架构，禁止跨层调用                            | **强制** |
| R05 | 使用参数化查询，禁止 SQL 拼接。db存储层采用mongodb         | **强制** |
| R06 | HTTP 响应使用统一 JSON 格式                      | **强制** |
| R07 | 所有错误必须显式处理                               | **强制** |
| R08 | 敏感信息禁止硬编码                                | **强制** |
| R09 | 代码变更同步更新文档                               | **强制** |
| R10 | 关键的流程增加INFO日志，异常出错流程增加ERROR日志            | **强制** |
| R11 | 编码前先思考：不确定时要询问，不要默默选择一种解释就直接开始           | **强制** |
| R12 | 代码最简化，任何过度设计都一目了然                        | **强制** |
| R13 | 只修改必要的部分，不要顺便修复旁边的代码                     | **强制** |
| R14 | 在开始前将模糊的指令转化为可验证的目标                      | **强制** |
| R15 | 进程的内存占用，有没有限制key的数量上限，对于很久不活跃的key，要主动淘汰掉 | **强制** |
| R16 | 内存或者db清理的时候，根据key关联的其他内存或者db数据要一起清理      | **强制** |
| R17 | web前端以及app客户端传的每个参数都必须校验                 | **强制** |
| R18 | 所有异常分支，都日志打印下err                         | **强制** |
| R19 | 错误码的定义要规划化，统一用宏定义收拢到一个文件中                | **强制** |
| R20 | 所有http接口，输入参数与返回字段的命名规则都统一用小写+下划线的蛇形命名法  | **强制** |
